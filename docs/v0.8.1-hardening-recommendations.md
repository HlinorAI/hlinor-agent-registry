# v0.8.1 Post-Release Hardening Recommendations

## Purpose

This document records the findings discovered during the read-only technical
review of `hlinor-registry` v0.8.0 after publication.

The v0.8.0 release is valid and materially improves the project. The three
fail-open cases identified before the release were fixed, the fixes have
regression coverage, and the published wheel matches the tagged source.

The findings below are additional hardening work. They should be addressed in
v0.8.1 before describing the package as a fully production-grade security
boundary.

## P1: Runtime silently skips malformed typed policies

### Confirmed behavior

`load_policy_rules()` treats several malformed compiled entries as though they
were declarative prose:

- the policy entry is not an object;
- `config` is absent or not an object;
- `kind` is unknown;
- `trigger` is not a list.

It also filters non-string trigger values instead of rejecting the policy.

An entry with no `kind` is legitimately declarative. An entry that contains a
`kind` but cannot become a runtime rule is not declarative; it is a broken
enforcement control and must fail closed.

### Reproduction

A valid bundle was compiled from the repository manifest. The compiled
`refund-requires-approval` policy was then changed from:

```json
{
  "kind": "requires_approval"
}
```

to:

```json
{
  "kind": "unknown_kind"
}
```

The integrity digest was recomputed to isolate policy validation from digest
validation.

Observed result:

```text
loaded_rules: []
allowed: true
reason: EXPLICITLY_ALLOWED
matched_policy_ids: []
```

The agent still declared the policy, but runtime enforcement disappeared.

### Threat model

The official compiler rejects an unknown handler kind, so this is not reachable
through the normal authoring path.

It remains important because:

- a compiled bundle may be produced by another implementation;
- a custom signing pipeline may sign a malformed bundle;
- an unsigned development bundle can be edited and re-digested;
- a future compiler/runtime version mismatch can produce an unsupported shape.

A valid signature authenticates the signer and bytes. It does not prove that
the policy is semantically enforceable.

### Required behavior

Runtime loading must distinguish:

1. a prose-only policy with no `kind`, which remains declarative;
2. a typed policy with a supported and valid configuration;
3. a malformed typed policy, which rejects the entire bundle.

Do not convert malformed typed policies into
`declarative_policy_ids`.

### Recommended implementation

Validate the complete compiled policy configuration during
`load_policy_rules()`:

```python
kind = config.get("kind")

if kind is None:
    continue

errors = policy_definition_errors(config)
if errors:
    raise ValueError(f"Invalid compiled policy {policy_id!r}: " + "; ".join(errors))
```

The runtime validator should additionally require:

- policy IDs are non-empty strings;
- each typed policy entry is an object;
- `config` is an object;
- `trigger` is a non-empty list;
- every trigger item is a non-empty string;
- the handler kind is supported;
- the required specification section is an object;
- all required fields are present;
- all field-level types and numeric ranges are valid.

Do not build a trigger tuple with:

```python
tuple(item for item in trigger if isinstance(item, str))
```

Filtering changes invalid configuration into a valid but weaker policy.

Use exact validation followed by:

```python
tuple(trigger)
```

### Agent policy references

The runtime should also reject non-string entries in an agent's `policies`
list. Filtering them out can silently remove a declared contract.

Unknown string policy IDs may remain declarative for backward compatibility,
but the distinction should be explicit:

- ID absent from the bundle: declarative reference;
- ID present as prose-only policy: declarative policy;
- ID present as malformed typed policy: bundle load error.

### Required tests

- unknown typed-policy kind rejects the bundle;
- malformed `config` rejects the bundle;
- non-list trigger rejects the bundle;
- empty trigger rejects the bundle;
- a non-string trigger item rejects the bundle;
- a missing required typed-policy field rejects the bundle;
- an invalid numeric field rejects the bundle;
- non-string agent policy references reject the bundle;
- a policy with no `kind` remains valid declarative context;
- a valid typed policy still loads and enforces normally.

### Acceptance criteria

- No malformed typed policy can become a declarative policy silently.
- No malformed typed policy can disappear from an agent's runtime rules.
- A checker is never created from a bundle containing an invalid typed rule.
- The load error names the policy ID and invalid field.

## P1: Publication is not gated by complete tagged CI

### Confirmed behavior

Both workflows react independently to a tag push:

```text
Tests & Validation
Publish Release
```

There is no dependency between the workflows. Package publication can begin
while the full Python matrix and integration jobs are still running.

For v0.8.0, both workflows passed and the package is correct. Their successful
ordering was incidental, not enforced.

### Risk

PyPI distributions are immutable. If a tagged commit fails:

- Python compatibility;
- LangChain or CrewAI integration;
- secret or public-scope scanning;
- signed-bundle smoke testing;
- package installation;

the package may already have been published before the failure becomes visible.

### Preferred implementation

Extract the common verification jobs into a reusable workflow:

```yaml
on:
  workflow_call:
```

Invoke it from:

- the push and pull-request workflow;
- the release workflow.

In the release workflow, make publication depend on every required job:

```yaml
publish:
  needs:
    - scope-scan
    - test
    - crewai-integration
    - langchain-integration
    - package
```

An acceptable simpler implementation is to place the full release-candidate
test suite directly in the release workflow before the publish job.

Do not rely only on a separate workflow having run for the same SHA unless the
release job retrieves and verifies the exact successful check suite for the
tagged commit.

### Required tests and checks

- simulate a failed matrix job and confirm `publish` is skipped;
- confirm the release workflow checks the tagged commit, not the branch tip;
- confirm package publication receives only artifacts built after successful
  verification;
- retain the tested wheel as a workflow artifact;
- publish the exact tested wheel instead of rebuilding it in another job.

### Acceptance criteria

- A failing required check makes publication impossible.
- The artifact sent to PyPI is the artifact that passed package verification.
- The tag, tested commit, built artifact, and published artifact form one
  traceable chain.

## P1: Protect release tags and remove ambiguous `skip-existing`

### Confirmed behavior

The release workflow uses:

```yaml
skip-existing: true
```

The accompanying comment treats a moved or re-pushed tag as a harmless retry.
The current repository ruleset protects the default branch but does not protect
release tags.

GitHub also reports the v0.8.0 release as non-immutable.

### Risk

Consider this sequence:

1. `v0.8.0` publishes source A to PyPI.
2. The tag is moved to source B.
3. The workflow runs again.
4. PyPI correctly refuses to replace source A.
5. `skip-existing` treats this as success.
6. Verification installs version `0.8.0` and checks only the version string.

The workflow can be green while GitHub tag `v0.8.0` and PyPI version `0.8.0`
contain different source code.

### Required behavior

A release tag is immutable identity, not a movable deployment pointer.

Once published:

- the tag must not move;
- the tag must not be deleted;
- the release must not silently attach to different source;
- a duplicate publication attempt should fail unless the workflow proves the
  existing artifact has the expected digest.

### Recommended implementation

1. Add an active tag ruleset matching:

   ```text
   refs/tags/v*
   ```

2. Block tag updates and deletion.
3. Restrict tag creation to the release workflow or a small release role.
4. Remove `skip-existing: true`, or replace it with explicit digest
   verification.
5. Enable immutable GitHub Releases if available for the repository.
6. Do not automatically edit an existing release from a repeated tag event.

For an idempotent retry:

1. query PyPI for the version;
2. retrieve the SHA-256 digest of the published wheel and sdist;
3. compare them with the retained release artifacts;
4. succeed only when every digest matches;
5. fail loudly on any mismatch.

### Required tests

- moving an existing `v*` tag is rejected;
- deleting an existing `v*` tag is rejected;
- duplicate publication with identical digests is an explicit no-op;
- duplicate publication with different digests fails;
- GitHub Release source commit equals the Git tag commit;
- PyPI artifact digests are recorded in the release output.

### Acceptance criteria

- A version string identifies exactly one source commit and one artifact set.
- A moved tag cannot produce a green release workflow.
- Release retries cannot hide source drift.

## P2: Reject non-finite policy numbers

### Confirmed behavior

This policy passes `validate-policy`:

```yaml
type: policy
id: invalid-freshness
kind: requires_approval
trigger:
  - send
requires:
  max_age_seconds: .nan
```

Observed result:

```text
Policy is valid.
```

PyYAML parses `.nan` and `.inf` as floating-point values. The current check:

```python
max_age <= 0
```

does not reject NaN because every ordered comparison with NaN is false.

Canonical JSON generation later rejects non-finite values, so the official
compile path remains fail-closed. The defect is a disagreement between
validation and compilation rather than a published-bundle bypass.

### Recommended implementation

Require a finite positive number:

```python
import math

if (
    not isinstance(max_age, (int, float))
    or isinstance(max_age, bool)
    or not math.isfinite(max_age)
    or max_age <= 0
):
    errors.append(f"policy: {section}.max_age_seconds must be a finite positive number")
```

Apply the same finite-number rule to every current and future floating-point
policy field.

### Required tests

Reject:

- `.nan`;
- `.inf`;
- `-.inf`;
- zero;
- negative values;
- booleans;
- numeric strings.

Accept:

- positive integers;
- positive finite floats.

Exercise both `validate-policy` and `compile`.

### Acceptance criteria

- Validation and compilation agree on every numeric boundary.
- Non-finite values receive a field-specific validation error.
- No traceback or generic canonicalization error is exposed to the CLI user.

## P2: Require meaningful review on protected branches

### Current rules

The active default-branch ruleset currently provides:

- pull requests required;
- required status checks;
- branch must be up to date;
- deletion prohibited;
- non-fast-forward updates prohibited;
- review conversations must be resolved.

This is a substantial improvement over an unprotected branch.

### Remaining gap

The ruleset currently requires:

- zero approving reviews;
- no CODEOWNERS review;
- no last-push approval.

The repository's current PR history is empty, so v0.8.0 itself does not have a
review trail.

### Recommended implementation

For `main`:

- require at least one approving review;
- dismiss stale approvals after new commits;
- require approval of the most recent push by someone other than its author;
- require CODEOWNERS review for security-sensitive paths;
- keep required conversation resolution.

Suggested CODEOWNERS scope:

```text
/hlinor_registry/policies.py
/hlinor_registry/policy_checker.py
/hlinor_registry/signing.py
/hlinor_registry/action_request.py
/hlinor_registry/decision.py
/.github/workflows/
/pyproject.toml
/registry/schema/
```

If the project currently has only one maintainer, document the temporary
exception instead of representing zero approvals as a completed review
control. Add a second trusted reviewer before making approval mandatory.

### Acceptance criteria

- Security-sensitive changes cannot merge without independent review.
- Review requirements apply to administrators unless a documented emergency
  bypass is used.
- Every future release commit has a PR and review record.

## P2: Protect the PyPI deployment environment

### Current state

Publishing correctly uses PyPI Trusted Publishing through GitHub OIDC. No
long-lived PyPI token is stored in the workflow.

The `pypi` GitHub environment currently has:

- no protection rules;
- no required reviewers;
- administrator bypass enabled.

### Recommended implementation

- add a required environment reviewer;
- limit deployment branches and tags to protected release tags;
- disable administrator bypass if operationally practical;
- use a short environment wait timer if the project needs an emergency
  cancellation window;
- keep `id-token: write` scoped only to the publish job.

### Acceptance criteria

- Only a protected release tag can request PyPI credentials.
- Publication requires the intended human or automated release approval.
- Non-release workflows cannot obtain the PyPI OIDC publishing identity.

## P2: Add artifact provenance

### Current state

The release pipeline:

- verifies tag and package version equality;
- builds wheel and sdist;
- runs Twine validation;
- publishes through OIDC;
- installs the exact version from PyPI;
- checks package and import versions.

This is a good baseline, but no provenance attestation or retained artifact
digest currently binds the published files to the GitHub build.

### Recommended implementation

- upload the verified wheel and sdist as immutable workflow artifacts;
- generate GitHub artifact attestations for both distributions;
- record wheel and sdist SHA-256 digests in the GitHub Release;
- optionally publish an SPDX or CycloneDX SBOM;
- verify the PyPI-reported digests after publication;
- retain the workflow run URL and commit SHA in release metadata.

### Acceptance criteria

- A consumer can verify which repository, workflow, commit, and tag produced
  each distribution.
- The release page records the same hashes PyPI reports.
- The publish job consumes the previously tested artifacts.

## P3: Unify compiled-policy runtime validation

### Problem

Authoring validation and runtime validation currently enforce different
subsets of the typed-policy contract.

Authoring validation checks:

- handler kind;
- trigger syntax;
- required fields;
- boolean field types;
- evidence type shape;
- failure threshold values.

Runtime loading currently performs only selected structural and boolean
checks. This duplication makes future drift likely.

### Recommended design

Use one domain-level policy contract validator in both places:

```text
YAML adapter -> shared policy validation -> compile
JSON bundle adapter -> shared policy validation -> runtime load
```

The adapters may produce different error presentation, but the domain
invariants must be shared.

Possible structure:

```python
def validate_policy_config(
    data: Mapping[str, Any],
    *,
    allow_prose_only: bool,
) -> list[PolicyValidationError]: ...
```

Each error should provide:

- stable machine-readable code;
- policy ID;
- field path;
- human-readable message.

Avoid generating a second independent runtime schema that can drift from the
authoring validator.

### Acceptance criteria

- The same malformed typed policy is rejected by authoring and runtime paths.
- Tests are parameterized across YAML and compiled JSON representations.
- New policy fields require one validation implementation and shared tests.

## Recommended implementation order

### Patch release blockers

1. Reject malformed compiled typed policies.
2. Make publication depend on successful tagged CI.
3. Protect release tags and remove ambiguous `skip-existing` behavior.

### Hardening

4. Reject non-finite policy numbers.
5. Publish the exact artifact that passed package testing.
6. Add artifact digest verification and provenance.
7. Add PyPI environment protection.
8. Require independent review for protected paths.
9. Consolidate authoring and runtime policy validation.

## Definition of done

v0.8.1 hardening is complete when:

1. a malformed typed policy cannot disappear from enforcement;
2. runtime and authoring validation enforce the same typed-policy invariants;
3. a release cannot publish until every required check passes;
4. release tags are immutable;
5. the tested artifact is the published artifact;
6. GitHub and PyPI artifact digests are verified and retained;
7. all new regression tests pass across Python 3.10 through 3.13;
8. the release commit has a protected PR and review trail.

## Current release conclusion

v0.8.0 remains a successful release. The published artifact matches its tag,
all required tests passed, and the previously identified typed-policy blockers
were fixed correctly.

Until the P1 findings in this document are addressed, the recommended
deployment profile is:

> Controlled production use with the official compiler, signed bundles, a
> deployment-owned trust store, and a reviewed release process.

Do not yet treat v0.8.0 as a hostile-input-safe policy compiler/runtime boundary
for arbitrary third-party compiled bundles.
